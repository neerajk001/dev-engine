# Taste
- Prefers a plan-first workflow: before implementation, wants the agent to read the project's spec/design docs (README, ARCHITECTURE, DECISIONS, ROADMAP) and produce a plan for the next milestone/version (e.g., "plan the v1"), then implement only after the plan is settled; again answered "yes." to entering plan mode for the next phase (V3 + TUI) and approved the written plan before any code was touched. Confidence: 0.85
- When starting a new subsystem (e.g., a TUI), wants the realistic options surveyed from least to most ambitious (e.g., hand-rolled ANSI → @clack/prompts → Ink) with a clear recommendation, then a structured choice on approach and timing — not the agent unilaterally picking and starting to build. Confidence: 0.7
- Wants new UI/features built only on a verified core: agreed to first run live end-to-end smoke tests (real API key, scratch copy of the fixture outside the repo with a seeded bug) before building the TUI, rather than layering UI onto code never exercised live. Confidence: 0.6
- Builds the product in roadmap phase increments: treats each version/milestone (V1, V2, …) as a gated deliverable and moves to the next phase only after the current one is done — appreciates the agent flagging unmet Definition-of-Done items (e.g., a live end-to-end smoke test not yet run) and settling scope up front (chooses the full/recommended scope) before planning the next phase; e.g., before allowing a new TUI to be built on the core, agreed to first run live V1/V2 end-to-end smoke tests against a scratch fixture outside the repo (real API key, seeded bug). Confidence: 0.7
- Prefers menu-driven terminal UIs over command-driven ones: explicitly rejected typing commands like `/optimize` or `/exit` and wanted actions (optimize, exit, model selection) as separate visual menu items navigable with arrow keys, with clear separation between the input area and action triggers. Confidence: 0.9
- Uses Claude Code and Codex CLI as the UX reference model for terminal interfaces: expects input to clear after submission, execution history to remain visible (scrollable or persistent), and the common-path action to be a single keystroke (e.g., Enter = do the obvious thing) — explicitly said "like claude code or codex." Confidence: 0.85
- Prefers explicit user control over automatic actions: wants optimization to remain as an explicit menu action button rather than being auto-triggered by Enter, even if it means more steps in the workflow; values deliberate action selection over convenience shortcuts. Confidence: 0.85
- Slash commands typed in a CLI/TUI should be intercepted and handled by the client itself, never forwarded to the agent/LLM as task input — discovered when `/traces` was sent to the agent as a task and returned "blocked"; the fix was to intercept it in the input handler before dispatch. Confidence: 0.65
- Expects feature parity across interfaces: when a feature is added to the CLI (e.g., `/traces`), it should also be wired up in the TUI — gaps between interfaces are treated as bugs, not acceptable omissions. Confidence: 0.55
- Comfortable deferring optional/plausible-scope features to keep momentum: when finishing a roadmap phase, prefers to mark nice-to-have items (e.g., the SSE web dashboard) as "deferred by choice" and advance to the next phase rather than build them ("for now lets move to v5"). Confidence: 0.5
